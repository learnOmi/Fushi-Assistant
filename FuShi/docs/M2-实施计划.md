# 浮时 FloatTime · M2 实施计划（数据与提醒引擎）

> 依据：`浮时-软件设计文档.html`（v1.0 设计基线）第 2、3、8 章。
> 前置：M1 已交付并验证（托盘常驻 + 悬浮窗可拖动/置顶/悬停展开 + 空课表）。
> 本文件是开发前置计划，不是代码。落地顺序：**M2a（地基）→ 验收 → M2b（引擎与上屏）**。

## 一、当前阶段与目标

### 所处阶段
M1 交付物是一个"能跑但空"的壳：托盘 + 悬浮卡片存在，但没有任何数据源，倒计时/进度条/下一节三个要素全是折叠的空骨架。M2 的使命是把壳接上"数据"和"会打断人的引擎"——这是产品定位（行为触发器）真正的起点。

### M2a 目标（本计划主战场：先还债，再打地基）
1. **偿还 M1 架构债**：M1 是纯代码后置 + 手搓的 WinForms `NotifyIcon`，与设计文档 4.2（MVVM + H.NotifyIcon.Wpf）不符。M2 要加领域逻辑，如果不先迁到 MVVM，逻辑会直接堆进 `WidgetWindow.xaml.cs`，之后越还越难。
2. **建立存储层**：SQLite + EF Core，落地设计文档 2.1 的 8 张表 + 迁移。
3. **实现三个纯领域算法**（设计文档 3.2 领域层）：周期展开、去重、错过补偿。这三块是引擎可靠性的根，必须先有测试保护再进引擎。
4. **验收门槛**：`dotnet test` 全绿；`dotnet build` 0 警告 0 错误；应用启动后托盘/悬浮窗行为相比 M1 不退步。

### M2b 目标（M2a 验收后启动）
1. 提醒引擎后台线程：扫描 → 睡到下一触发点 → 触发 → 唤醒补偿。
2. 通知通道：Windows Toast（CommunityToolkit）+ 自绘弹窗骨架（设计文档 ADR-4 双通道）。
3. 数据上屏：悬浮组件四要素接真实数据（科目 / 倒计时 / 进度条 / 下一节）。

### 明确不在 M2 范围（留在 M3/M4）
主窗口周网格编辑、阶段管理 UI、统计页、导入导出、多屏/DPI 打磨、打包自启。M2 只做"引擎 + 数据 + 让悬浮组件显示真实内容"，不做编辑界面。

## 三、技术选型理由（含与设计文档的偏差说明）

### 3.1 存储：EF Core 而非 Dapper（沿用已锁定决策）
- 领域是**关系型**（Phase/Entry/Subject/Occurrence 多表关联），不是"取一堆行"。
- **迁移**：8 张表在 M2→M4 还会变（加字段、加索引），EF Migrations 是版本化改表的最低成本手段，Dapper 得自己写 SQL 迁移脚本。
- **统计（FR-5）**：完成率/科目分配天然是 LINQ 聚合，EF 表达力更顺。
- 性能在这个量级（个人、单机、几百条 Occurrence）不是问题，选型不看性能看"改表成本 + 查询表达力"。
- **强制约束**：必须用 `AddDbContextFactory` + 每次操作短生命周期 `DbContext`。`DbContext` 非线程安全，引擎在后台线程、UI 在 UI 线程，共享实例会随机炸。

### 3.2 调度：`Task.Delay` + 可取消 CTS（**偏离设计文档 4.2**）
设计文档 4.2 表格写的是 `PeriodicTimer`，但 3.4 正文与 ADR-6 明确要求"睡到下一个触发点"（省电、事件驱动）。二者语义冲突：`PeriodicTimer` 是**固定周期**，退化为轮询，违背 ADR-6 且耗电。

**结论**：以 3.4/ADR-6 为准，用 `Task.Delay(到下一触发点的时长, linkedToken)`，课表改动时通过 `CancellationTokenSource.Cancel()` 立即唤醒重排。这是对文档 4.2 表格的**有意修正**，需在设计文档里标注（第八节③）。

### 3.3 时间模型：本地墙钟 + IANA 时区
存本地墙钟时间（`Kind=Unspecified`）+ IANA 时区 ID，不存 UTC。原因：跨英/中两地、且要正确处理英国夏令时切换——"周三 19:45 数学"存本地时间才符合课表语义。展开时：
- `TimeZoneInfo.IsInvalidTime`（英国 3 月跳过的 1 小时）→ 顺延到该日**第一个有效时刻**，并记日志，**绝不静默丢弃**。
- `TimeZoneInfo.IsAmbiguousTime`（英国 10 月重复的 1 小时）→ 取**第一个**（DST 侧）。
- 跨午夜条目（`EndTime < StartTime`）→ 视为**一个连续时段**，不拆两天。

### 3.4 整体分层
照设计文档 3.2 的 Presentation / Application / Domain / Infrastructure 四层。M2 只落下 Domain + Infrastructure + Presentation 三层的**骨架**，Application 层的引擎在 M2b 补。

## 四、实现策略

### 4.1 三个纯领域算法（M2a 核心，先测后接）
纯函数式，不碰数据库、不碰系统时钟（`now` 由调用方传入），可 100% 单测。

**① 周期展开 `RecurrenceExpander`**
输入：`ScheduleEntry` 模板、`Phase` 生效日期区间、目标日期区间 `[from, to]`、时区。
输出：`IReadOnlyList<PlannedOccurrence>`（含 `PlannedAt` 本地墙钟 `DateTime`）。
关键处理：
- 按 `DayOfWeek` 在区间内逐日匹配；
- 用日期 + `StartTime` 组装 `DateTime`，再过 `TimeZoneResolver` 归一化（DST）；
- 跨午夜：结束时刻落在次日；
- 与 `Phase` 区间取交集，`Enabled=false` 的模板跳过。

**② 去重 `OccurrenceDeduplicator`**
输入：已有 `Occurrence` 集合 + 新展开集合。
输出：只包含"尚未存在"的集合。键 = `(SourceType, SourceId, PlannedAt)`。
与数据库唯一索引双保险：算法层去重（内存，省往返），数据库唯一索引兜底（并发/重放）。

**③ 错过补偿 `MissedCompensator`**
输入：`since`（上次正常扫描时刻）、`now`、区间内的计划项、宽限期 `GraceMinutes`。
输出：三类判决 ——
- 已触发过（`FiredAt != null`）→ 不动；
- `plannedAt ∈ [now-Grace, now]` → **立即补发**（刚错过，还来得及提醒）；
- `plannedAt < now-Grace` → 标记 `Missed`，**合并成一条汇总摘要**（"过去 3 小时错过 2 条"），避免一口气弹一堆。
宽限期来自 `ReminderRule.OffsetMinutes`/`AppSetting.LeadTimeMinutes`。

### 4.2 存储层
- `DbContext` 只做映射与索引，不塞业务逻辑；
- 迁移用 `dotnet ef migrations add InitialCreate`（设计时工厂指向 `%APPDATA%` 或临时路径）；
- 首次启动 `context.Database.Migrate()` 建库/升级；数据库损坏或缺失时自动重建（NFR-6 自恢复）。

### 4.3 MVVM 迁移（M2a 第一件事）
- `App.xaml.cs` 改为构建 `IHost`（`Microsoft.Extensions.Hosting`），注册 `DbContextFactory`、服务和各 ViewModel；
- 托盘用 `H.NotifyIcon.Wpf` 的 `TaskbarIcon`（XAML 声明 + `ViewModel` 命令/菜单），删掉 `MakeTrayIcon()` 手绘代码（图标改为资源）；
- `WidgetWindow` 只留**纯视图职责**：拖动（`DragMove`）、悬停计时（200/300ms）、命中判定。这些是真正的视图行为，**不强行搬进 VM**；
- 数据/状态（科目、倒计时、进度、下一节、`IsExpanded` 内容态）搬进 `WidgetViewModel`（`ObservableObject`），视图用绑定消费；
- 倒计时刷新：UI 侧 `DispatcherTimer` 每秒调 `ViewModel.Refresh(DateTime now)`，VM 本身保持纯 `net8.0`、可测、不依赖 WPF 计时器。

> 关键口径：**MVVM ≠ 把一切都塞进 VM**。偶然视图行为（拖动、悬停计时）留在视图是对的；把"业务/数据状态"留在代码后置才是债。

### 4.4 验收方式
- `dotnet build FuShi/FuShi.sln -c Debug --nologo` → 0 警告 0 错误；
- `dotnet test` → 全绿；
- 启动 `FuShi.exe` → 进程存活、托盘出现、悬浮窗可拖动/悬停展开不退步（XAML 错误只在运行时暴露）。

## 五、状态管理方式

| 状态 | 归属 | 机制 |
|---|---|---|
| 持久化数据（8 表） | SQLite 文件 `%APPDATA%\FuShi\fushi.db` | EF Core 迁移管理 schema；每次操作短生命周期 `DbContext`（工厂创建） |
| 悬浮窗位置/透明度/时区/免打扰等设置 | `AppSetting` 单行表 | 取代 M1 的 `widget.json`；读写走仓储 |
| 引擎运行时态（内存最小堆、下一触发点） | 引擎对象内存 | M2b；易失，进程退出即弃，靠 `Occurrence` 表恢复账本 |
| Occurrence 生命周期 | `Occurrence` 表 | 状态机 `Pending→Fired/Skipped/Snoozed/Done/Missed`，`FiredAt`/`SnoozeUntil` 落地 |
| UI 状态（展开态、当前显示内容） | `WidgetViewModel` | `ObservableProperty` 绑定 |
| 线程上下文 | 无 `ThreadLocal` | 引擎后台线程 ↔ UI：`DbContext` 用工厂隔离；跨线程回 UI 用 `Dispatcher.Invoke` |

事务边界：单次"写 Occurrence + 更新状态"在一个短事务内完成；展开/补偿纯计算不占事务。

## 六、组件调用关系

```
启动 (App.OnStartup)
  └─ 构建 IHost / ServiceProvider
       ├─ 注册 FuShiDbContextFactory  (SQLite)
       ├─ Application 服务           (课表服务 / 事项服务 / 统计服务 —— M2b 起)
       ├─ ReminderEngine             (Scheduler —— M2b)
       └─ WidgetViewModel
  └─ Database.Migrate() 建库/升级
  └─ TaskbarIcon (H.NotifyIcon) 常驻托盘
  └─ WidgetWindow.Show()  ← 绑定 → WidgetViewModel

数据流（M2a 打通"读"；M2b 打通"算/触发"）：
  SQLite ──EF Core──► 仓储 ──► 课表服务 ──► WidgetViewModel ──绑定──► 悬浮组件

引擎循环（M2b，设计文档 3.4 / ADR-6）：
  ┌─► ScanOverdue()            顶部每轮都扫（覆盖漏掉的 Resume / 手动改时钟 / DST 跳变）
  │     └─ 未处理且已过期 → 走 MissedCompensator 判决
  │   peek 最小堆 → 取下一触发点
  │   compute delay → await Task.Delay(delay, linkedToken)
  │        └─ 被 _reschedule.Cancel() 打断 → OperationCanceledException → continue 重排
  └─ Fire()：写 Occurrence(Fired) → 派发通知 → 刷新 WidgetViewModel → 回到 ScanOverdue()

唤醒补偿（M2b）：
  SystemEvents.PowerModeChanged(PowerModes.Resume)
     └─ 仅调用 _reschedule.Cancel()   ← 该事件跑在系统隐藏窗口的消息泵线程上，
                                          处理器内禁止触碰 UI / DbContext
```

## 七、潜在难点与风险及对策

| # | 难点/风险 | 对策 |
|---|---|---|
| 1 | **DbContext 非线程安全**：引擎后台线程与 UI 线程并发访问 | 强制 `AddDbContextFactory` + 短生命周期实例；禁止把 `DbContext` 注入为单例/被多线程共享 |
| 2 | **DST 边界**：英国 3 月跳过 1 小时、10 月重复 1 小时，展开可能静默丢课或错 1 小时 | `TimeZoneResolver` 显式处理 `IsInvalidTime`/`IsAmbiguousTime`；单测覆盖 2026-03-29 与 2026-10-25 切换日 |
| 3 | **跨午夜条目** | 明确"一个连续时段、不拆两天"规则并写进 `RecurrenceExpander` 与测试 |
| 4 | **唤醒后错过补偿**：休眠/关机/重启/手动改时钟 | `ScanOverdue()` 放在引擎循环**顶部**每次必跑，不只依赖 Resume 事件；补偿合并为单条摘要防弹窗轰炸 |
| 5 | **SystemEvents 回调用错线程** | `PowerModeChanged` 处理器**只**调 `_reschedule.Cancel()`，不碰 UI/DbContext |
| 6 | **未打包桌面应用的 Windows Toast 需要 AUMID** | M2b 验证 `ToastNotificationManagerCompat` 在非打包进程能否弹；不行则降级为 H.NotifyIcon 气泡或自绘弹窗，并把结论写回设计文档 |
| 7 | **MVVM 迁移后行为回退** | 迁移与功能分开提交，逐项回归（拖动/悬停/位置记忆），先保证 M1 行为等价再加数据 |
| 8 | **迁移工具链**：`dotnet-ef` 未装 / 交叉编译 | 安装 `dotnet-ef` 工具；`EnableWindowsTargeting` 已在 csproj，测试工程用纯 `net8.0` 规避 WPF |
| 9 | **结构变更影响构建命令** | 多工程后 `dotnet build FuShi/FuShi.sln` 不变；`dotnet test` 指向测试工程 |
| 10 | **精度/省电**：定时器精度与 CPU 占用 | 用"睡到下一触发点"而非轮询（ADR-6）；下一触发点密集时再评估，先用设计文档基线 |

## 八、待你拍板的关键取舍

### ① 项目拆分粒度
- **A. 多工程（推荐）**：`Domain` / `Infrastructure` / `App` / `Tests` 四工程。分层由编译器强制，领域测试跑纯 `net8.0`（快、不依赖 WPF）。代价：多 3 个 csproj、多一层引用维护。
- **B. 单工程 + 文件夹**：全部留在 `FuShi.App`，用 `Domain/`、`Infrastructure/` 文件夹分。最省事，但分层靠自觉，测试工程被迫 target `net8.0-windows`。
- 我的倾向：**A**。领域算法是本项目唯一"值得被测试保护"的资产，值得为它单独建工程。

### ② 是否现在引入 Serilog
- **A. M2a 就引入**（文件 sink，日志落 `%APPDATA%\FuShi\logs`）：DST 顺延、补偿判决、引擎异常都需要留痕，user_rules 也要求"不允许吞异常、至少记日志"。代价：多两个包。
- **B. 先用 `Debug.WriteLine`/简易文件日志，M4 再上 Serilog**：更轻，但引擎排障会缺上下文。
- 我的倾向：**A**。

### ③ 设计文档 4.2「PeriodicTimer」的修正

### 落地记录（与计划的偏差说明）

- **触发时刻口径 = `Occurrence.PlannedAt`，未接 `ReminderRule.OffsetMinutes`。** 计划 4.1③ 写「宽限期来自 `ReminderRule.OffsetMinutes` / `AppSetting.LeadTimeMinutes`」，但 M2 没有录入 `ReminderRule` 的任何界面，规则表的 `TriggerType` / `OffsetMinutes` / `Channels` 全无数据来源；而 `MissedCompensator` 与 `Occurrence` 唯一索引都按 `PlannedAt` 定义。故 M2b 把「何时触发」直接定为课表条目的开始时刻（`PlannedAt`），`ReminderRule` 表保留 schema、不接入引擎，留到 M3 编辑界面再启用。**这是有意简化，不是遗漏。**
- **展开视野的 off-by-one 修正。** `RecurrenceExpander.Expand` 的 `[from, to]` 是双闭区间；原 `to = from + EXPANSION_HORIZON_DAYS` 实际覆盖 8 天，导致同一个周几在视野内落两次（由集成测试捕获）。改为 `to = from + (EXPANSION_HORIZON_DAYS - 1)`，恰好 7 天；`App.ReloadWidget` 的时间线请求同步对齐。
- **引擎落在 `FuShi.Infrastructure`（纯 `net8.0`），而非计划第六节的「Application 层」。** 目的是让引擎不依赖 WPF、可被 `FuShi.Tests` 直接引用做单测；与 UI 解耦靠 `INotificationChannel` 接口 + `ScheduleChanged` 事件，App 只负责装配并把回调编组回 UI 线程。
- **通知分流规则（ADR-4 双通道落地）。** `NotificationService.Dispatch`：`Soft` 只记日志；命中免打扰时段则只走 Toast；否则自绘弹窗，`Strong` 再追加 Toast。`IsQuietNow` 支持跨午夜窗口。
- **风险 6 结论（Toast AUMID）。** `ToastNotificationManagerCompat.CreateToastNotifier()` 在非打包进程返回成功，日志出现「Toast 通道可用（AUMID=FuShi.FloatTime.Desktop）」，即**探测通过**；「能否真正弹出」需运行期首次派发才能确认，实现已做失败自动降级 + Warning。配套约束：App TFM 必须提到 `net8.0-windows10.0.18362.0`（否则 NuGet 只给 `net5.0` 资产、拿不到 `ToastNotificationManagerCompat`）。结论已回写到 `浮时-软件设计文档.html` 的 ADR-4 下方。
- **唤醒补偿兜底位置。** `MaterializeAsync` + `ProcessDueAsync` 放在引擎循环**顶部**、每轮必跑，不依赖 `Resume` 事件；`PowerModeChanged` 处理器**只**调 `RequestRescan()`（该回调跑在系统隐藏窗口的消息泵线程，禁止碰 UI / DbContext）。
- **VM 保持纯 `net8.0` 可测。** 宿主/引擎把 `TimelineSlot` 快照推给 `ApplySchedule`，UI 侧 `DispatcherTimer` 每秒 `Refresh(now)` 只在缓存上做纯投影，不打数据库。
