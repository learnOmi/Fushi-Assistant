## 一、当前阶段与目标

### 所处阶段：产品闭环是断的

M2 交付后，系统长这样：库里 8 张表、领域三算法 + 时间线取景、后台引擎准点触发、Toast/自绘弹窗双通道、悬浮组件接真实数据。**唯独缺一头：没有任何界面能把课表写进库。**

这不是"少个功能"，是"产品不成立"——M2b 做运行期验证时，我们只能**手工改 SQLite** 塞两条测试课表进去，才看到引擎动起来。用户实际拿到手，打开就是个功能齐全但**永远空**的东西：悬浮组件显示「点击添加第一个时段」，可那个"点击"没有落点。

所以 M3 的第一使命不是"加页面"，是**把「录入 → 展开 → 上屏 → 触发 → 反馈」这条链闭合**。UI 是手段，闭环是目的。

### M3a 目标（本计划主战场：先把课表喂进去）

1. **主窗口骨架**：可打开、可关闭（关闭即隐藏不退出，设计 4.x）、单例、位置记忆。
2. **周网格课表视图（FR-1.1 / FR-1.2，Must）**：7 天 × 时段的可视网格，点击进入编辑。
3. **时段编辑**：新增 / 修改 / 删除一条 `ScheduleEntry`（科目、起止时间、备注、启用与否）。
4. **科目与阶段的最小可用**：能创建/选择科目（否则条目没科目可挂）；自动自举一个生效 `Phase`（否则条目没容器）。完整"阶段切换器"留 M4。
5. **收尾动作**：任何一次编辑落库后，**触发一次「对账」（重展开 Occurrence）+ 唤醒引擎 + 刷新悬浮组件**，让改动立刻反映到提醒与上屏。
6. **验收门槛**：`dotnet test` 全绿；`dotnet build` 0 警告 0 错误；**全流程手工走通**——新建科目 → 加一条 5 分钟后的时段 → 到点真的弹提醒 → 悬浮组件显示该科目。

### M3b 目标（M3a 验收后启动）

1. **设置页**（FR-2.4 / FR-3.5 / FR-6.4）：透明度、免打扰时段、提前提醒分钟数、主题、时区。这些字段 `AppSetting` 里全有，M2 只落了"位置"，M3b 把其余接上界面。
2. **提醒交互落地（FR-3.1 / FR-3.2 / FR-3.3，Must）**：M2b 的自绘弹窗目前是**骨架**（只有标题/时间、无按钮行为）。M3b 把三按钮接上——开始→计时；稍后→推后生成子 Occurrence；跳过→记 `Skipped`；并把"开始/跳过/完成"写进 `CompletionLog`。
3. **"结束前 N 分钟预告"**：接通 `LeadTimeMinutes`（全局默认）到引擎，让提醒不只发生在开始时刻。
4. **主窗口补齐页签**：课表 / 设置两页可用；事项 / 统计按 5.5 原型保留页签占位。

### 明确不在 M3 范围（留在 M4）

- **阶段管理 UI**（FR-1.4，新建/切换/一键换课表全套）——M3a 只做"自动自举一个阶段"，不做阶段切换器。
- **统计页**（FR-5.1/FR-5.2）——M3b 只负责把原料（`CompletionLog`）正确写进去，不做可视化。
- **多屏 / DPI 打磨**（FR-2.4 多屏、NFR-4）——M3 保持"当前主屏可用"。
- **打包与开机自启生效**（FR-6.1）——设置里有开关、UI 可改，但注册表写入与安装包留 M4。
- **导入导出**（FR-1.5，Could）、**事项页**（FR-4.1/4.2，Should）——继续后置。

## 三、技术选型理由（含与设计文档的偏差说明）

### 3.1 主窗口用原生 WPF，不引 UI 框架

设计文档 5.7 定了视觉规范（品牌绿、科目色、8/12px 圆角、4 档间距、亮/暗双色）。这些用原生 WPF `ResourceDictionary` + `Style` 完全能落，不需要引入 MaterialDesign/HandyControl 之类整包 UI 框架。

理由：① 本项目 UI 面很窄（一块悬浮卡 + 一个主窗口），框架带来的体量（内存、包体）与 NFR-1（空闲内存 <150MB）、NFR-7（包 <50MB）相冲突；② 视觉规范是自己定的颜色系统，套框架反而要跟它的主题体系打架；③ 悬浮组件在 M1/M2 已经是手写样式，主窗口沿用同一套资源字典，视觉才统一。

**代价**：格子、按钮、TabControl 的样式要自己写（一次性成本）。可接受。

### 3.2 编辑交互：模态对话框 + 命令，不上"对话框服务"

编辑一条时段就是"弹个框、填完、确定/取消"，`ShowDialog()` 的返回值 + `DialogResult` 就够。不引入 `IDialogService` 抽象——那是为了"可测的对话框流程"，而我们真正要测的是 `EntryEditorViewModel` 的校验逻辑（纯 VM，能测），对话框本身是薄壳，不值得为它加一层间接。

`MainWindowViewModel` 里发命令，视图（`MainWindow.xaml.cs`）负责 `new EntryEditorDialog{ DataContext = vm }.ShowDialog()`，结果回灌 VM。**视图做"弹框"这种偶然行为是对的位置，不是债。**

### 3.3 模板改动 → 必须做 Occurrence 对账（**这是 M3 的技术核心**）

M2 的 `MaterializeAsync` 只会"补缺"（[ScheduleService.cs](file:///c:/Users/Administrator/FuShi-Assistant-.Net/FuShi/src/FuShi.Infrastructure/Scheduling/ScheduleService.cs#L52-L119) 只 `AddRange` 新增），**从不删除**。

这在"只有固定课表、从不改动"的 M2 里没暴露，但 M3 一放开编辑就出事：用户把周三 19:45 的数学改成 20:00，库里那条 19:45 的 `Pending` Occurrence **还在**——到点会弹一个"已经不存在的课"的提醒（幽灵提醒）。删条目同理，留一堆孤儿 `Pending`。

所以 M3a 必须补一个对账动作，口径定死：

```
编辑某条 ScheduleEntry（改时间/改科目/停用/删除）
  └─ ReconcileAsync(sourceId 集合)
       ├─ 删除该 SourceId 下 所有 PlannedAt > now 且 Status == Pending 的 Occurrence
       ├─ （若模板仍启用）重新展开该模板未来视野内的实例，落库
       └─ 不动 PlannedAt <= now 的、不动任何 Fired/Missed/Skipped（历史即事实，不回填）
```

一句话口径：**"改模板只影响未来，已发生的账本不改写"**。这个规则要写进注释。

### 3.4 偏差：托盘左键语义（M3 修正）

设计文档第 6 章写的是"托盘**左键唤起主窗口**；右键菜单：暂停提醒/打开课表/退出"；而 M2 实现成了"左键 toggle 悬浮窗"（`ToggleWidget`，见 [App.xaml.cs](file:///c:/Users/Administrator/FuShi-Assistant-.Net/FuShi/src/FuShi.App/App.xaml.cs#L265-L282)）。M3 有主窗口了，把左键改回设计口径：**左键 → 打开/唤起主窗口**；悬浮窗显隐挪到右键菜单。这是有意修正，需在设计文档里备注。

## 四、实现策略

### 4.1 M3a 录入闭环（顺序即依赖）

1. **`ScheduleEditService`（写服务）**：`EnsureActivePhaseAsync`（自举）、`Subject` CRUD、`ScheduleEntry` CRUD。每方法短生命周期 `DbContext`（沿用 M2 工厂约束）；写成功后返回受影响 `SourceId`，供对账用。
2. **`ScheduleService` 补两块读**：
   - `GetWeekGridAsync(phaseId, weekStart)`——按"天 → 该天模板列表"分组，供网格渲染（比用扁平 timeline 更好：网格要的是**模板**，不是已展开实例）。
   - `ReconcileAsync(IReadOnlyList<int> entryIds)`——按 3.3 口径删旧、重展开。
3. **`WeekGridViewModel`（纯投影）**：把"天+模板"揉成固定的 7×N 网格数据（行 = 阶段内出现过的**去重起始时刻**排序，列 = 周一…周日），并标记"当前时段"。**纯 net8.0，先写测试**。
4. **主窗口 + 网格视图**：`MainWindow` 壳 + `WeekGridView`。点空格子 → 以该天、该行时段为预填 → 开 `EntryEditorDialog`。
5. **编辑对话框 + 科目对话框**：`EntryEditorViewModel` 做校验（起止不能相等；跨午夜给提示而非报错；科目必选）。
6. **收尾管线**：任何编辑成功后走一条统一方法 `AfterScheduleChanged()` —— `ReconcileAsync` → `engine.RequestRescan()` → `ReloadWidget()`。**一处收口**，别在每个命令里各写一遍。
7. **验收：手工全流程**（见 4.3）。

### 4.2 M3b 设置与提醒交互

1. **设置页**：透明度滑块（实时预览悬浮窗）、免打扰起止、提前提醒分钟数、主题、时区下拉。写回 `AppSetting` 后，需要重载悬浮窗/引擎的即时生效一部分（如时区改了要重展开）。
2. **提醒弹窗三按钮**：`开始` / `稍后 10min` / `跳过`。
   - 稍后：生成一条**子 Occurrence**（设计 5.6「稍后提醒生成新的子 Occurrence」）——需要决定子实例的 `SourceType/SourceId` 归属（见第八节取舍 ④ 的邻接问题）。
   - 跳过：`Occurrence.Status = Skipped` + 写 `CompletionLog(Status=Skipped)`。
   - 开始：进入"进行中"，到 `EndsAt` 写 `CompletionLog(Status=Done)`（或用户手动"完成"）。
3. **提前量接入引擎**：触发时刻 = `PlannedAt - offset`，`offset` 优先取条目上的 `ReminderRule.OffsetMinutes`，无则用 `AppSetting.LeadTimeMinutes`，都为 0 则就是开始时刻（M2 行为）。
4. **页签补齐**：课表/设置两页 + 事项/统计占位。

### 4.3 验收方式

- `dotnet build FuShi/FuShi.sln -c Debug --nologo` → 0 警告 0 错误；
- `dotnet test FuShi/tests/FuShi.Tests/FuShi.Tests.csproj` → 全绿（M2 基线 40 个 + M3 新增）；
- **手工闭环验收（M3a 关键，必须真跑）**：
  1. 删掉 `%APPDATA%\FuShi\fushi.db`，冷启动 → 进入主窗口课表页 → 自动出现「默认课表」阶段；
  2. 新建科目「测试科」→ 在**今天 `now + 2 分钟`**（跨天则选合适周几）加一条时段；
  3. 看悬浮组件 3 秒内出现该科目；到点收到提醒；
  4. 回主窗口把该条目时间 +1 小时 → 确认**旧时刻不再触发**（验对账）；
  5. 删除该条目 → 悬浮组件回到空态、无幽灵提醒。
- **M3b 追加**：设置页改免打扰时段 → 到点提醒降级为 Toast；弹窗点"跳过" → DB 里该 Occurrence 为 `Skipped` 且 `CompletionLog` 多一行。

## 五、状态管理方式

| 状态 | 归属 | 机制 |
|---|---|---|
| 课表数据（阶段/科目/条目） | SQLite | `ScheduleEditService` 写，`ScheduleService` 读；短生命周期 `DbContext` |
| 主窗口生命周期 | `App` | 单例，**按需创建**，关闭即 `Hide()` 不 `Close()`（设计 4.x：关主窗口不结束进程） |
| 周网格展示态 | `WeekGridViewModel` | 由"天+模板"投影而来，纯计算；编辑后整体重取重算（不做细粒度 diff） |
| 编辑中的表单态 | `EntryEditorViewModel` | 对话框生命周期内；确定才落库，取消即丢 |
| 设置项 | `AppSetting` 单行表 | 读走 `AppSettingRepository`；写后按需重载引擎/悬浮窗 |
| 引擎待触发点 | 引擎内存堆 | 编辑后靠 `RequestRescan()` 打断睡眠重排（M2 已具备） |
| 提醒响应（开始/稍后/跳过） | `Occurrence` + `CompletionLog` | 状态机 `Pending→Fired→(Done/Skipped/Snoozed)`；稍后落新实例 |
| 线程上下文 | 无 `ThreadLocal` | UI 线程写库用 `ConfigureAwait(false)` 同步等待（M2 已有先例：`PersistPosition`）；跨线程回 UI 用 `Dispatcher.BeginInvoke` |

事务边界：一次编辑（改模板 + 对账删旧 + 重展开）**尽量放在同一方法调用序列**里，但允许"删旧"和"重展开"分两个短事务（重展开是幂等的、唯一索引兜底）。**不引入跨表大事务**——为了"编辑原子性"去抱一个大事务，性价比低，且与短生命周期上下文约束冲突。

## 六、组件调用关系

```
启动 (App.OnStartup)
  ├─ BuildHost：注册 AppSettingRepository / ScheduleService / ScheduleEditService / 各 VM
  ├─ DatabaseInitializer.MigrateOrRebuild()
  ├─ CreateTray / CreateWidget / StartEngine          （M2 既有）
  └─ ❌ 不预创建 MainWindow（按需创建，设计 4.x）

打开主窗口（托盘左键 / 悬浮组件双击 / 展开态「打开课表」）
  └─ MainWindow.Show()
       └─ MainWindowViewModel.LoadAsync()
            ├─ ScheduleEditService.EnsureActivePhaseAsync()   ← 自举阶段
            ├─ ScheduleService.GetWeekGridAsync(phaseId, weekStart)
            └─ WeekGridViewModel 投影 → 绑定

编辑一条时段
  EntryEditorDialog.ShowDialog() → EntryEditorViewModel.Validate()
       └─ 确定 → ScheduleEditService.UpsertEntryAsync()

                   ├─ ScheduleService.ReconcileAsync([sourceId])   ← 删未来 Pending + 重展开

                        └─ 引擎 ScheduleChanged 事件 → Dispatcher.BeginInvoke → 同一条刷新

提醒响应（M3b）
  ReminderPopupWindow 按钮 → NotificationService / ScheduleService
       ├─ 稍后 → 生成子 Occurrence（PlannedAt = now + 偏移）
       ├─ 跳过 → Occurrence.Status = Skipped + CompletionLog(Skipped)
       └─ 开始 → 进入进行中 → EndsAt 写 CompletionLog(Done)
```

## 八、待你拍板的关键取舍

### ① 周网格的形态（**M3a 最核心决策**）

设计文档 5.5 原型画的是"7 列 × 4 行"，但那 4 行（06:45 / 通勤 / 19:45 / 21:45）其实是**那套示例课表里出现过的 4 个时段**，不是固定刻度。落到实现有三条路：

- **A. 动态行网格（推荐）**：行 = 当前阶段里出现过的**去重起始时刻**（升序），列 = 周一~周日，单元格 = 该行该天的科目。点空格子 → 用"该天 + 该行时刻"预填编辑框。
  - 优点：最贴近原型，行数随真实课表自适应；点格子预填能大幅减少录入成本。
  - 代价：新增一条"没出现过的时刻"要用「+ 添加时段」按钮，不能靠点空格子（因为那行不存在）。
- **B. 时间轴网格**：行是连续刻度（如 06:00–23:00，15/30 分钟一格），块高按时长。
  - 优点：直观、像真日历；拖拽（FR-1.3）时更顺。
  - 代价：渲染与命中复杂度陡增，大量空格浪费纵向空间，且我们 M3 不做拖拽——性价比低。
- **C. 列表式**：每天一列，纵向列出该天所有条目（不依赖"公共时刻"）。
  - 优点：实现最简单，任意时刻都能塞。
  - 代价：丢掉"一眼看出周节奏"的价值，与原型不符。

我的倾向：**A**。它既贴合原型，又把"点格子 = 快速录入"这个体验做出来了；B 的复杂度留给 M4 若真要做拖拽再评估。

### ② M3 主窗口铺几个页签

- **A. 只铺"课表 + 设置"两页（推荐）**：事项/统计页签不出现，等 M4 用真东西再上。克制，不给用户点进去一片空的体验。
- **B. 一次铺满四页**：事项/统计挂"即将推出"占位，界面结构与设计 5.5 对齐。
- 我的倾向：**A**。空占位页签对个人自用工具是纯噪音；页签结构随时可加。

### ③ 科目 / 阶段的创建入口放哪

- **A. 内联（推荐）**：科目在编辑对话框的科目下拉里"新建"（下拉底部一个「+ 新建科目」）；阶段完全自举、M3 不给 UI。
  - 优点：符合"主窗口只用来改课表"的定位，最少的点击路径；不打断录入流程。
  - 代价：没有集中的"科目管理"视图（想统一改色/改名要去各自条目）。
- **B. 独立管理入口**：设置页下挂"科目管理""阶段管理"。
  - 优点：集中、清爽。
  - 代价：多两级导航；阶段管理又是 M4 范围，现在做等于提前背包袱。
- 我的倾向：**A**。

### ④ 提醒规则（`ReminderRule`）在 M3 启用到什么程度

- **A. 只接"全局提前量"（推荐）**：M3b 只管 `AppSetting.LeadTimeMinutes`（全课表一个提前量），引擎触发点 = `PlannedAt - LeadTime`。`ReminderRule` 表继续闲置到 M4。
  - 优点：改动面最小，只动引擎一处；默认 0 时与 M2 行为等价，回归风险低。
  - 代价：没法"这节提前 5 分钟、那节提前 15 分钟"。
- **B. 全面启用 `ReminderRule`**：每个时段可配提前量、通道（Toast/弹窗/声音/闪烁）、强度（按科目分档，设计 7 章的"按科目分档"决策）。
  - 优点：完整兑现 FR-3.1/3.2 与"按科目分档"。
  - 代价：编辑对话框要加一组提醒配置 UI；引擎触发点计算、去重键（`PlannedAt` 还是 `triggerAt`）都要跟着改，M2b 那条"触发时刻 = `PlannedAt`"的口径被推翻——**改动外溢到 M2 的账本语义**，得同步迁移数据模型。
- 我的倾向：**A 起步**，把"按科目分档"留到 M3b 末尾或 M4。理由是 M2b 刚把 `PlannedAt` 钉死、风险 6 刚实测结案，M3 再去动引擎的触发语义，会把这轮稳定性白费。

### 运行期发现与修复（2026-10-18）

> 这一节是"必须真跑"的价值证明：下面这个缺陷编译期与单测都发现不了。

**缺陷：二次启动崩溃（`App.OnExit` 空引用）。**
M3a 改 `App.xaml.cs` 后，`OnStartup` 的顺序是「单实例互斥体判定 → `base.OnStartup` → `_logger = LoggingSetup.Create()`」。当第二个实例启动时，互斥体判定失败走 `Shutdown()` 分支，此时 `_logger` 尚未赋值（仍为 `null!`），`Shutdown()` 触发的 `OnExit` 里第一句 `_logger.Information("浮时退出")` 直接抛 `NullReferenceException`，进程被未处理异常终止并弹出 WER 崩溃报告。

- 定位手段：Windows 事件日志 `.NET Runtime` Event 1026 给出栈 `at FuShi.App.OnExit(ExitEventArgs e)`；再对照 `OnStartup` 赋值顺序即可确认。
- 修复：把 `_logger = LoggingSetup.Create();` 提到 `OnStartup` **首句**（互斥体判定之前），并在二次实例分支补一条「已有实例在运行，二次启动退出」日志。
- 回归验证：二次实例现以 **ExitCode=0** 干净退出，Windows 事件日志无新 APPCRASH；主动实例日志照常。

**附带澄清（曾被误判）：** 早前把"启动无日志"错误归因于"某个旧 `dotnet` 进程占用互斥体"。实际那个 PID 是 OmniSharp（C# 语言服务器），与互斥体无关。真实原因是上面的空引用崩溃——二次实例在写日志之前就崩了。此外 Serilog 文件 sink 默认非共享，二次实例的日志行会被静默丢弃（主实例持有文件），这也是"看不到日志"的帮凶；**该项未改**（`shared: true` 会把日志割裂成 `_001` 等多个文件，得不偿失）。

**缺陷 2：周网格整片空白（WeekGridView 继承了错误的 DataContext）。**
现象：保存时段成功、对账与提醒都正常（日志可证），但主窗口课表页**只有表头、没有数据行**。
根因：`MainWindow.xaml` 中 `<views:WeekGridView .../>` **未指定 DataContext**，继承到窗口的 `MainWindowViewModel`；而 `WeekGridView.xaml` 内部 `ItemsSource="{Binding Rows}"` 的 `Rows` 只存在于 `WeekGridViewModel`（即 `MainWindowViewModel.Grid` 属性）上。绑定源缺失 → WPF **静默失败**（不抛异常），数据行整片空白。表头 `{Binding DayHeaders}` 恰好在两个 VM 上都有 → 照常渲染，掩盖了故障。
- 定位手段：对照 `MainWindow.xaml` 的 DataContext 继承链与 `WeekGridView.xaml` 的绑定路径，确认 `Rows` 在窗口 VM 上不存在；再用日志确认数据确实已落库（排除持久化问题）。
- 修复：`WeekGridView` 的 `DataContext` 改绑 `{Binding Grid}`；可见性另用一层 Grid 持有窗口 VM 的 `IsEmpty`（避免与网格 VM 的 `IsEmpty` 语义混淆）。
- 教训：WPF 绑定失败是**静默**的，编译期与单测都拦不住；凡是"自定义控件 + 换 DataContext"的地方，都应显式声明 DataContext，不要依赖继承。
